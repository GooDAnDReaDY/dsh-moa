# План: разбиение lib/client.js (issue #47)

Статус: принято решение, реализация отложена до появления подтверждённой механики бандлера.
Дата: 2026-09-11. Исполнитель: zcode. Связанная issue: #47.

## Контекст

Корневой чек-лист code review требует файл ≤800 строк; `lib/client.js` — ~1240 строк
после батча качества. `MoAEditor` ≈500 строк, словари ≈110 строк, CSS ≈85 строк.
Прямое разбиение упирается в механику клиентского бандлера DSH.

## Собранный evidence (2026-09-11)

1. **Харнесс отдаёт ровно один модуль на пакет**: на тест-контуре (DSH 0.1.5-rc.2)
   клиент плагина обслуживается по единому URL
   `/plugins/??@goodandready/dsh-moa/client.js&rev=<hash>` (combo-загрузчик);
   реестр модулей в индекс-странице ссылается только на `client.js` пакета.
2. **Ни один плагин семейства не использует относительный require в клиентском
   коде**: dsh-lanmode (23 файла в lib/), dsh-tts (client.js 1851 строка),
   dsh-model-sync (17 файлов), dsh-clinebot (5 файлов), dsh-grok-xsearch (14
   файлов) — везде `require('./...')` в client.js отсутствует. Многофайловость
   живёт только в серверной половине.
3. Клиентская factory получает `require` (пакетные зависимости: `react`,
   `@deepseek-ai/dsh-client-ui-primitives`) — документированных свидетельств
   поддержки относительных require внутри клиентского модуля нет.

## Варианты

- **A. Оставить один файл (принято сейчас).** Нулевой риск для загрузки карточки;
  известный компромисс с чек-листом зафиксирован в issue.
- **B. Сборочная склейка (concat/минимальный bundler перед `npm pack`).** С.Split
  исходников на части + prepublish-скрипт, собирающий `lib/client.js`.
  Плюс: файлы в репозитории маленькие, публикуется по-прежнему один модуль.
  Минус: в семействе нет ни одного плагина со сборочным шагом — вводит новую
  конвенцию, усложняет publish-пайплайн и локальную отладку.
- **C. Относительный require в клиенте.** Самый чистый вариант, но требует
  подтверждённой поддержки в бандлере харнесса (эксперимент на тест-контуре).

## Решение и критерии пересмотра

- Сейчас — вариант A: риск поломки загрузки карточки выше пользы, а файл после
  батча качества сократился (1240 строк против 1311) и остаётся цельным по смыслу.
- Пересмотреть к варианту C, если появится подтверждённый пример относительного
  require в клиентском модуле любого плагина семейства (эксперимент: маленький
  пакет-проба `require('./client-part.js')` на тест-контуре + проверка загрузки
  карточки без ошибок в консоли).
- Пересмотреть к варианту B, если файл превысит ~1800 строк или в семействе
  появится первый плагин со сборочным шагом.

## Чек-лист разбиения (когда механика подтверждена)

1. Вынести словари и `makeT` в `lib/client-dict.js`, стили — в `lib/client-styles.js`,
   `SearchableModelPicker` — в `lib/client-picker.js`.
2. `lib/client.js` остаётся единственной точкой входа `__ModuleLoader__.load`.
3. Проверки: клиентский модуль отдаётся 200 по per-plugin URL; карточка
   рендерится (settings.plugin.item) без ошибок в консоли; локали регистрируются;
   HMR/обновление соседнего плагина не ломает стили (атрибут data-dsh-plugin).
